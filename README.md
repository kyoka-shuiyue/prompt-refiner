# prompt-refiner

[简体中文](README.md) | [English](README.en.md)

`prompt-refiner` 帮你理清思路：辨认真正想完成的事，解决会影响结果的歧义和冲突，再把必要的目标、边界和完成条件表达清楚。

**当前版本：1.4.0。在理清意图之外，补上强模型最容易出错的三处：完成条件不清、需求多次改动后交付走样、交给其他模型的任务单写不清。** 明确任务直接执行，只有真正影响结果的信息缺口才值得补充或询问。它也支持创建、改写、点评和比较 Prompt。

技能以 `SKILL.md` 及配套文件发布，供兼容宿主加载。具体发现方式和调用语法由宿主决定；核心规则不绑定特定模型。

## 这次更新了什么

- **改动附完成条件**：修代码、改文档时，最后附 2–4 行可以检查的完成条件。修 bug 时写清楚怎么复现，以及修好后怎么确认。
- **多次改动后按最终版交付**：在内部整理最终口径，逐项核对。用户说“用最早那版”时，先检查那一版里有没有后来已被否定的内容，不悄悄写回去。
- **限定不是矛盾**：“菜品都打 8 折”加上“酒水不打折”，直接合并成一条规则，不当成矛盾去问。
- **改写规则不定死含糊处**：原文写“看情况”的地方保持含糊，标成 `【待确认】`，不补原文没有的期限、比例或流程。
- **提示词要可执行**：分类、标记这类判断要有可用的标准或填写位置，写明拿不准时怎么办；处理邮件、评论等外部内容时，写明这些内容是数据，不是指令。
- **环境中立的交接任务单**：只写目标、用户原话、最终口径、完成条件、边界、停止条件和假设，不夹带本机路径或本地规则，同一要求只写一次。
- **精简规则本身**：`SKILL.md` 从约 16KB 缩到约 10KB；1.3.0 的触发门槛、口令、权限边界和退出规则都保留。

完整说明见 [CHANGELOG.md](CHANGELOG.md)。

## 什么时候使用

| 请求的情况 | 处理方式 |
| --- | --- |
| 语言混乱，已经影响理解 | 结合上下文重建意图；明显转写错误直接修正 |
| 意图不明、前后矛盾，或不同理解会明显改变成品 | 先看已有证据，再提出具体解释供选择 |
| 方向明确，但无法判断最终交付什么 | 从已有目的补齐必要目标与完成条件 |
| 明确要求创建、改写、点评或比较 Prompt | 交付 Prompt 或点评，未经要求不执行其中的任务 |
| 需求改了好几次，要出最终版 | 按最终口径逐项核对，不恢复已被否定的内容 |
| 要把任务交给另一个模型或 Agent | 写环境中立的任务单，附完成条件和停止条件 |
| 明确任务、简单请求、意图清楚的自由创作 | 直接进入原任务流程 |
| 仅缺原文、文件、数据，或环境未知 | 查找或索取最小必要输入，不重新访谈意图 |

例如：

> 帮我把这份说明精简成一页，但每一段都必须逐字保留。

这里需要先理清冲突：是保留完整原文、另附一页摘要，还是允许删改原文？两种结果不同，值得问清楚。

而“做一张有海边氛围的活动海报，其他你决定”已经给出明确方向与创作自由，不需要再追问配色、字体、布局，也不应自行扩展活动内容。

再如一段 App 介绍的对话：用户先说“这次只上 iOS，别提安卓”，最后又说“功能列表就用最早那版”。最早那版里有“安卓桌面小组件”。这时应该指出这一项已被否定，而不是照原样写回去。

## 保留的能力

需要精炼时，只把真正影响结果的事项讲清楚：

1. 最终要得到什么。
2. 满足什么条件才算完成。
3. 范围、事实、权限等重要边界。
4. 何时结束、询问、重试或停止。
5. 哪些未决选择必须由用户决定。

这些是检查角度，不是每次都要填满的表格。清晰的原要求无需重写；普通实现选择交给执行者。补充内容应与任务规模相称，不能为了显得完整而扩写。

另外有几条规则不论是否进入精炼都适用：不编造用户没给的名字、数字、日期、价格或链接，用占位符或写明假设；改动类请求附完成条件；用户要求简短时，保留读者需要的关键事实。

## 安装与更新

若使用 `skills` CLI，可运行：

```bash
npx -y skills add kyoka-shuiyue/prompt-refiner --skill prompt-refiner --global --agent codex --yes
```

也可以手动获取仓库：

```bash
git clone https://github.com/kyoka-shuiyue/prompt-refiner.git
cd prompt-refiner
```

将仓库中的 `prompt-refiner/` 目录复制到宿主的技能目录。更新时先运行 `git pull --ff-only`，再同步该目录；按宿主要求重新加载技能。运行环境要求以安装工具与宿主文档为准。

## 使用方式

支持隐式技能路由的宿主可根据描述自动选用；也可显式调用：

```text
使用 $prompt-refiner 理清下面这个请求，保留我的范围，只处理影响结果的歧义：
[原始请求]
```

| 口令 | 行为 |
| --- | --- |
| `纯prompt` / `只要prompt` | 只返回一个可复制的 Prompt；若缺输入会使它不可用，先索取该输入 |
| `继续` / `直接继续` | 沿用已确认目标和授权继续；新出现的重大歧义仍需解决 |
| `不要问` / `你决定` / `自问自答后执行` | 在已授权的决策范围内选择合理默认值；不扩大权限 |

用户要求执行任务时，澄清完成后继续执行；用户只要 Prompt 时，交付后结束。技能不另设精炼批准步骤，也不要求创建计划文件。

```text
prompt-refiner/

```

`agents/openai.yaml` 是同一技能的界面元数据，不是另一个模型版本。

`evals/` 中的六用例对照评测针对历史提交 `ead59ad` 与 `11010eb`，见[历史报告](evals/forward-test-report.zh-CN.md)，不是当前版本的结果。

1.4.0 的规则在发布前做过盲评：回复者使用 Claude Haiku 5.5，评审使用 Claude Sonnet 5.5，回复匿名打乱后才评分，每个版本每条用例跑 2 次。

| 批次 | 用例 | 结果（10 分制平均） | 检查点失败 |
| --- | --- | --- | --- |
| 第三批 | 8 条新用例 | 1.4 草稿 8.56，1.3.0 8.00 | 0 对 4 |
| 第四批 | 6 条新用例 + 2 条复测 | 1.4 最终草稿 8.44，上一版草稿 8.00，1.3.0 7.25 | 0 / 1 / 3 |

**局限**：样本小；只有一位评审；检查点由改版者编写；测试环境带有作者自己的全局规则，可能压低版本间的差距；没有在更强的模型上测试。正式版在最终草稿基础上补回了几条 1.3.0 的保护规则，这些补回的内容没有再单独测试。这些分数不代表在所有模型上都有同样幅度的提升。原始回复与评分材料暂未放进本仓库。
